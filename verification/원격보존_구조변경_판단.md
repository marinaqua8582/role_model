**추천은 C의 설계 검토다. 아직 구현·서비스 도입하지 않는다.** A는 로그인 응답 전달 대체의 시험 후보이고 B는 이동 위험이 낮지만, 인증/receipt/flush와 미분류 시간이 계속 전역 큐에 남는다. 작은 최적화 반복으로25명 동시 저장을 충분히 빠르게 만든다는 근거가 없으므로 C가 최종 목표에 더 부합한다. PostgreSQL 같은 영속 transaction과 unique constraint를 지원하는 저장소를 예로 들지만 제공 업체·요금제·지역은 아직 선정하지 않았다. A/B를 구현하겠다는 승인으로 이 추천을 해석하지 않는다.

C의 최소 설계 조건:

- 학생 자료 기본키는 기존studentKey 및 자료 종류(Progress/Tests/Submissions). 중복 legacy를 자동 삭제하거나 새 키로 바꾸지 않고 충돌 자료는 별도 보존·검토한다.
- 같은 학생·종류의 저장은 row/version 조건부 갱신, expectedVersion 불일치409. 요청ID+본인+payload hash의 유일 제약을 두고 자료 갱신과 completed receipt를 같은 transaction으로 commit한다. 동일 요청은 같은 결과, 다른 payload는 거부한다.
- 취소 tombstone과 저장 receipt도 동일 학생 transaction에서 결정한다. 응답 유실 후에는 상태 조회만 수행하고 학생 저장 POST를 자동 반복하지 않는다. 다른 학생 자료 접근을 서버가 차단하고 본인 전체 Google ID만 반환한다.
- 서버 저장 완료는 권위 있는 원본 transaction commit 후에만 표시한다. DB가 원본이면 관리자도DB를 조회한다. Sheets 미러 반영을DB 완료와 혼동하지 않고, 기존 요구가 Sheets 반영 완료라면 그 계약을 별도로 정하기 전에는 전환하지 않는다.
- 미래의 이관은 별도 승인 후 비공개 원본 백업→기존 자료 읽기 호환→studentKey/소유권/필드별 hash 대조→제한된 전환으로 한다. 현재 운영 답안을 읽거나 이관한 것이 아니다.
- 롤백 때 과거 Sheets를 덮어써 최신 답안을 잃으면 안 된다. 전환 후 새 답안·receipt·버전을 보존하고 일시 쓰기 차단/정합성 확인 후 경로를 되돌리는 runbook이 먼저 필요하다. 새 답안을 읽는 호환 경로 없이 오래된 Sheets로 단순 복귀하지 않는다.
- 미래 검증은 합성25명 로그인·동시 저장·복원·최종 제출, 같은 학생 두 장치의 stale version/중복/취소 경합, commit 직후 응답 유실·서버 재시작, 관리자 조회, 기존 답안 읽기 호환 및 rollback 재현까지 포함한다. 성공100%/timeout·중복·오학생갱신·ID노출0 외에 수업 응답시간 기준을 먼저 합의한다(예: p95≤5초/최대10초는 제안이지 달성 실측이 아님).

공식 근거: [Apps Script API 실행 요건](https://developers.google.com/apps-script/api/how-tos/execute)은 OAuth·공통 standard Cloud·API executable를 요구하고 서비스 계정은 지원하지 않는다. [Sheets batch](https://developers.google.com/workspace/sheets/api/guides/batchupdate)는 요청 묶음 처리를 지원하지만 이것만으로 읽기-조건부 갱신의 학생별 transaction을 만들었다고 볼 수 없다. ## 필요한 사용자 판단

C의 설계를 구체화할지, 당분간A/B의 제한적 검토를 택할지 결정한다. C라면 외부 서비스 허용 여부·예산/지역·학교의 데이터 보관 기준·권위 있는 저장 원본·수업 응답시간 기준을 정해야 한다. 아직 credential 입력이나 운영 조작은 필요 없다. 원격 보존이 성공하면 별도 수동push는 필요 없으며 원본 이력 복구만 선택 사항이다. 불가능할 경우 최소 수동 조작은 최종 메시지에서만 안내한다.
