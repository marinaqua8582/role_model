## 응답 경로의 최소 수정

모든 proxy 응답은 원래 요청의 임의 transport nonce와 일치해야 전달한다. nonce는 신원·세션·비밀값이 아니며 fingerprint에서 제외하여 idempotency를 유지한다. Google content가 실행 endpoint로 돌아가는 GET을 차단한다.

확인된 content bounce 또는 nonce 불일치에 한해 기존75초 예산 안에서 동일 요청의 getSaveStatus를 최대1회 조회한다. 저장 POST를 재전송하지 않는다. ## 별도 검토가 필요한 다음 단계

응답 전송과 저장 직렬화는 서로 다른 문제다. 공식 문서는 ContentService가 일회성 script.googleusercontent.com URL로 리디렉션됨을 명시한다([Google Content service](https://developers.google.com/apps-script/guides/content#redirects)). 현재 실측으로 이 URL의404와 실행 URL 복귀를 확인했지만 Google 내부 사유는 미확인이다. 같은 URL/학생 저장 POST를 무조건 재시도하는 방식은 채택하지 않았다.

먼저 검토할 전송 대체안은 테스트 전용 Apps Script API scripts.run이다. ContentService 출력 객체 대신 JSON 기본 객체를 반환하고 Vercel이 API operation/result를 검증하는 경로를 별도 staging flag로 구성한다. 기존 웹앱 배포는 롤백용으로 보존한다. 공통 standard Google Cloud 프로젝트, Apps Script API 활성화, API executable 배포, 호출자 OAuth가 필요하고 서비스 계정은 지원되지 않는다([공식 실행 API 요건](https://developers.google.com/apps-script/api/how-tos/execute)). 현재 계정의 설정/권한이 준비됐다고 가정하지 않으며 새로운 OAuth 접근 승인은 Google 화면에서 사용자가 직접 해야 한다. 비밀값을 채팅/Git/브라우저 JS에 넣지 않는다. 전송 대체만으로 글로벌 lock 속도가 해결된다고 주장하지 않는다.

구체적 변경 범위는 테스트 GAS의 JSON 실행 entrypoint/공유 요청 처리, Vercel 학생 proxy 및 staging 제어 API의 서버 전송 adapter, private Preview OAuth 환경 설정, nonce·실행 오류·expired token·unknown write 회귀 검사다. 로그인 정책/저장 데이터 필드/기존 studentKey/시트 연결/학생 UI는 유지한다. test-only admin 확인→합성1명→5명→10명→25명 순서에서 실패하면 확대 중단하고 로그 분석한다. 이 범위는 별도 검토·접근 승인 전에 구현/권한 확대하지 않았다.

저장 성능은 그 뒤 Sheets batch/CAS 또는 학생별 영속 transaction 구조를 별도 비교한다. 운영 반영 조건은 최신 동일 소스·배포의 전체25명 성공100%/timeout·lock실패·중복·오학생갱신·ID노출0, 실제 UI 서버 확인→복원→최종 제출 완료, 사전 합의한 수업 응답시간 목표 통과, 비공개 백업·롤백 확보다. 현재는 이 조건을 충족하지 못했다.
